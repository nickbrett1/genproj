# 022 — batch-job container images: `language: shell` and `docker-container.workload`

**Status:** implemented (2026-10-21) — slices 1 (`workload: batch`), 2
(`language: shell`) and 3 (`imageVisibility`).

A scheduled backup runner for `ryzen` (UM790) has to be generated by genproj.
Its shape is a _batch job_, not a service: every bit of logic lives in the
image, Buildkite publishes it to GHCR, and Dagu on the host runs it as
`docker run --rm <image>:<sha>` on a schedule. No port, no health endpoint, no
long-running process, no application language in the genproj sense.

`docker-container` + `buildkite` is already most of the answer — multi-stage
buildx, registry cache, SHA + `latest` tags, the `org.opencontainers.image.source`
label, the locked secret scan, `aptPackages` in the runtime stage, and the
`command`/`entrypoint` → `scripts/<name>` copy contract. What is missing is
_defaulting_, not machinery. This spec records the four frictions and the
smallest change set that removes them, from
`projects/genproj/genproj-batch-job-container-images.md`.

The rule for the whole change set: **`workload: service` renders byte-identical
to today.** Everything here is an opt-in branch, not a rewrite.

## Friction 1 — there is no `shell` primary language

The `node` fallback cannot build a script-only repo (`COPY package.json …` fails
on the first `docker build`), and the `python` workaround builds but is red on
first push: the generated Buildkite python step starts with an unconditional
`python -m pip install -e ".[dev]"` and there is no `pyproject.toml`. `baseImage`
cannot rescue it either — the python build stage runs `python -m venv` against
the base.

**Design.**

1. `"shell"` joins the whitelist in `resolveProjectLanguage`
   (`src/generator/capability-template-utils.js:864`) and
   `configurationSchema.language` in `src/catalog/catalog.json`. **Done.**
2. `images.shell = "debian:bookworm-slim"` — glibc, consistent with the existing
   no-Alpine-by-default rule.
3. **Single-stage Dockerfile** for `shell`: `FROM` → `apt-get install` →
   `COPY scripts/` → `ENTRYPOINT`. There is nothing to compile, so a `build`
   stage that copies nothing into a `runtime` stage is noise. **Done** as
   `dockerfile-shell.template`, selected by `when` rather than by conditional
   placeholders inside the multi-stage template — that is what keeps a
   non-shell Dockerfile byte-identical.
4. CI for `shell`: no build/test step beyond the secret scan. `shellcheck -x
scripts/*.sh` is emitted only under a `code-quality-shell` capability —
   always-on would fail repos with deliberate `eval`/dynamic sourcing, and the
   generator does not gate its own script repos today.
5. No `devcontainer-*` required: `language` is project-level and legal with zero
   devcontainer capabilities.
6. Sonar and release artifacts need nothing: no mapping yields no
   `reportPaths` line (as `rust` already proves), and
   `singleArtifactPaths.shell = []` routes to the existing honest
   "no artifact paths configured — notes only" branch.

Out of scope for v1: a `binaries: [{name, url, sha256, target}]` download stage.
Until then the entrypoint installs and verifies its own pinned tarball, exactly
as `scripts/install-gitleaks.sh` already does.

## Friction 2 — `docker-container` is service-shaped and every default points the wrong way

`watchtower` and `homepage` default to `true` (guarded as
`config.x !== false`), `exposePort` defaults to `3000` and is emitted as `EXPOSE`
unconditionally, `publishPort` derives a `ports:` binding from it, and compose
hardcodes `restart: unless-stopped`. The correct batch configuration is
therefore five remembered `false`s, and forgetting one is silent — a watchtower
label on a backup image only surfaces as the wrong backup running against a
newer restic.

**Design — `docker-container.workload: "service" | "batch"`, default `service`.**

When `batch`, derive rather than ask:

| Setting                             | batch value                                                            |
| ----------------------------------- | ---------------------------------------------------------------------- |
| `watchtower`                        | `false`                                                                |
| `homepage`                          | `false`                                                                |
| `EXPOSE` / `ports:` / `portsConfig` | omitted entirely                                                       |
| `healthcheck`                       | `none`                                                                 |
| compose `restart`                   | `"no"`                                                                 |
| runbook                             | `docker run --rm` invocation, no published port, no Watchtower section |

One enum plus derived booleans. The capability is not forked, and `service`
stays byte-identical. Catalogue description gains a line so `batch` is findable
from the UI.

## Friction 3 — the smoke gate tests the wrong thing for a job

`docker_smoke` asserts "starts and serves HTTP" by polling `.State.Health`.
For a batch job the claim that matters is "runs and exits 0", and that
combination currently produces no gate at all.

**Design — a batch gate**, emitted when `workload: batch`:

```sh
docker run --rm <image>:<sha> --dry-run   # require exit 0
```

`--dry-run` is deliberate and is the **contract the generated entrypoint must
honour**: print the work it would do, do none of it, exit 0. Without it the gate
would run the real job on every pull request — a full backup per push is not a
smoke test. Argv placement matters: with a declared `ENTRYPOINT` `docker run`
arguments are appended to it, but with only a declared `CMD` they _replace_ it,
so `resolveBatchSmokeArgv` repeats the command before the flag.

Non-zero fails the step and prints the run's output. It runs on **every branch**
(as the service gate does), so a broken job fails the pull request rather than
the 3am run, and `docker_publish` gains it as a dependency. This is the most
valuable item here: it converts "the image builds" into "the job ran to
completion".

The service gate's conditions are unaffected — the batch branch is a separate
predicate, not a widening of `emitsSmokeGate`.

## Friction 4 — a host-pulled image needs pull credentials and the runbook does not say so

The runbook's credential story covers _pushing_. It tells the operator that "a
public repo yields a public package (no credentials needed for NAS/Watchtower
pulls)", which is true only when the repo is public. A private backup-runner
repo yields a private package and the pulling host (Dagu on `ryzen`) has no
credential — a runtime failure with no generation-time warning.

**Design — make `imageVisibility` real.** When it is not `public`, emit a
runbook section covering `docker login ghcr.io` on the pulling host with a
`read:packages` classic PAT, stating plainly that the image is not anonymously
pullable. **Done** for the service runbook; the batch runbook already documents
the same login. The section is appended inside an existing line, so `public`
renders byte-identically (the golden fixture still pins it). The value is already threaded into the template data; only the
emission is missing. Deleting the key and documenting the public assumption was
the alternative and was rejected as less useful.

## Cross-repo contract — make the mount set fail loudly

Scheduling (Dagu, in `dagu-dags`) and execution (this repo) meet at the **mount
set**: the DAG says `-v /volumeUSB1/...:/backup:ro`, the image expects `/backup`.
Neither repo's CI can check that.

**Requirement on the generated entrypoint:** assert every expected path exists
and is readable at startup, and exit non-zero naming the missing path. A
mismatch then fails run #1 with `/backup: not found` instead of silently
producing an empty backup. This is entrypoint-template guidance, not a README
paragraph.

Open question, answerable only on the infra side: does the Dagu container get a
Docker socket + CLI, or is a native `docker:` executor the right shape? It
decides whether this is a DAG edit or an infra change.

## Acceptance criteria

1. `language: "shell"` is accepted, produces a **single-stage** Dockerfile, and
   the generated CI is green on the first push of a repo containing only
   `scripts/*.sh`.
2. A generated `shell` + `docker-container` + `buildkite` project with
   `workload: batch` contains no `ports:`, no `EXPOSE`, no `homepage.*` label,
   no `watchtower` label, `restart: "no"`, and no `HEALTHCHECK`.
3. `workload: service` (and `workload` absent) renders **byte-identical** to
   today. Enforced by a new golden fixture pinning the current rendered
   Dockerfile, compose file, runbook and pipeline — there is no snapshot test
   suite to lean on, so this fixture is part of the work, not a precondition.
4. The batch smoke gate runs the image with `--rm`, fails on non-zero exit, runs
   on every branch, and `docker_publish` depends on it.
5. The Dockerfile copies `scripts/<name>` and `chmod +x`es it when `entrypoint`
   names `/usr/local/bin/<name>` — existing behaviour, re-asserted for `shell`.
6. A private-repo image is accompanied by an explicit host pull-credential
   section; no silent failure.
7. `docker build` of the generated repo succeeds and the generated pipeline is
   green with **no hand edits**. This is the criterion that kills the
   `language: python` workaround; assert it as a generation smoke test.

## Sequencing

1. **`docker-container.workload: batch`** — pure derivation plus template
   guards. Covers frictions 2 and 3. No new language, no new template file, and
   the byte-identical fixture from criterion 3 lands with it. **Done.**
2. **`language: shell`** with the single-stage Dockerfile — covers friction 1
   and the first-push-red problem. **Done.**
3. **`imageVisibility` made real** — documentation-shaped, can land any time.
   **Done.**

### Two consequences worth knowing

- **A shell container must declare an entry point.** Every other language has a
  default CMD derived from its build output; shell has no binary name to
  derive, so a guessed one is a container that exits 127 on its first run. The
  validator refuses instead.
- **Shell and a frontend are mutually exclusive.** A shell project scaffolds no
  server to serve the built assets, and the single-stage image has no build
  stage to build them in. Silently dropping the frontend would look like it
  worked, so the combination is rejected.

## Decisions taken

- `workload` is a key on `docker-container`, not a new `batch-job` capability:
  less duplication, `service` stays byte-identical, and a catalogue description
  update makes it discoverable.
- `shellcheck` is gated behind `code-quality-shell`, not always-on.
- `restart: "no"` for batch, including ad-hoc `docker compose` runs of the same
  image.
- Spec number 022, confirmed free.
