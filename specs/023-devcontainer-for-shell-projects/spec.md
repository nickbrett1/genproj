# 023 — a `language: shell` project opens as a devcontainer

**Status:** implemented (2026-10-23).

A repository generated by genproj could not be opened at all:

```
$ devcontainer up --workspace-folder .../um790-backup
Error: Dev container config (.../um790-backup/.devcontainer/devcontainer.json) not found.
```

The cause is not a stale checkout. `generateMergedDevelopmentContainerFiles()`
opens with `if (developmentContainerCapabilities.length === 0) return files;`,
and `language: shell` (spec 022, slice 2) is the one language whose projects
select **no** `devcontainer-*` capability — the shell slice made that legal on
purpose ("the deliverable is a script, not a toolchain"). There was no
`devcontainer-shell` to select, so a shell project could not get a
`.devcontainer/` even if its author asked for one. The generator produced a repo
that the container workflow rejects, which is a defect rather than a
configuration choice.

## What changed

| Piece                                    | Change                                                                                                                                                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `devcontainer-shell` capability          | New catalog entry (`provides: language = shell`, dependency `docker`, ShellCheck/shell-format/bash-ide editor extensions). The base every other language already had.                                                                   |
| `devcontainer-shell-json.template`       | Same shape as the python base minus the language runtimes: common-utils (zsh), `socat`, mounts, `postCreate`/`postStart`. `remoteUser` stays `vscode` — the base image's non-root user.                                                 |
| `devcontainer-shell-dockerfile.template` | `FROM mcr.microsoft.com/devcontainers/base:bookworm`, then the shared tooling the other bases carry (tmux built from source, oh-my-zsh + p10k, antigravity, goose iff `doppler`). No language runtime.                                  |
| `generateAllFiles()`                     | `language: shell` **implies** `devcontainer-shell` when nothing `devcontainer-*` is selected. The implication is applied to a local copy of the context, so the project's declared capability list keeps its meaning for CI and deploy. |
| `{{shellcheckInstall}}`                  | ShellCheck enters the image only with `code-quality-shell` — the same gate the CI step uses, so no repo has a lint tool it did not ask for.                                                                                             |
| `primaryDevcontainerCapabilityId()`      | Comment only: `devcontainer-${language}` now exists for shell too, so `shell` no longer relies on the selected-developer-container fallback.                                                                                            |

## Decisions

- **Implication, not a required selection.** Requiring the capability would
  leave the same failure one forgotten checkbox away, and the checkbox
  configures nothing a shell project chooses: there is no runtime to pick. Any
  project that declares `language: shell` gets the base.
- **Only shell is implied.** Other languages keep "no selection, no
  devcontainer" — that stays a deliberate choice there, where a capability
  really is a toolchain decision. Pinned by a test.
- **The base still follows the primary language (memo D8).** A shell project
  that also selected `devcontainer-python` keeps the shell base and merges the
  python _feature_ as a toolbox; the implication does not override a selection
  and does not reorder the base.
- **The devcontainer is not the deliverable.** A `docker-container` batch
  project's own image stays single-stage and port-less; `.devcontainer/` is the
  workspace, and it is an ordinary service container.

## Acceptance criteria

1. A `language: shell` project with no `devcontainer-*` capability emits
   `.devcontainer/` with `devcontainer.json`, `Dockerfile`, `.zshrc`,
   `.p10k.zsh`, `.tmux.conf`, `post-create-setup.sh`, `post-start-setup.sh`.
2. The emitted `devcontainer.json` parses, sets `remoteUser: vscode`, and
   declares no language-runtime feature.
3. The Dockerfile builds from `mcr.microsoft.com/devcontainers/base`.
4. `code-quality-shell` is the only thing that adds ShellCheck to that image
   (and its editor extension).
5. An explicit `devcontainer-*` selection is not overridden by the implication.
6. A non-shell language with no devcontainer selected still emits none.
7. The existing suite stays green (960 tests).

## Correction for the already-generated repository

`um790-backup` was generated before this change and has no `.devcontainer/`.
Regenerating it is not an option — its pipeline has been hand-edited well past
the generated shape (`retention_tests`, `dagu_pin_bump`) — so the fix there is
to add the generated `.devcontainer/` tree as a standalone commit.
